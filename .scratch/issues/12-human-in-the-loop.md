# 12: 人工介入 —— pending 文件是事实，GUI 只是另一个写入口

**What to build:** 人可以在任何时刻推进或拦住一次运行，而不打断它。意图以 pending 文件表达（提案、预算授权、暂停、代码基锚点），命令行与界面写的是同一条事实；没人应答时一定超时回落，绝不让一次无人值守永久挂在等人上。

**Blocked by:** 05（预算授权与暂停语义）

**Status:** resolved

- [x] 通过命令行往 pending 放一条意图，下一 tick 被采纳并落事件；意图被消费后不会重复生效。
- [x] 同一条意图也能从界面写入；两条路径写的是同一条事实，不产生两条互相矛盾的记录。
- [x] 无人应答时超时回落：超过时限后按预定默认值继续，事件里写明「回落」而不是「人工批准」。
- [x] 人工暂停只能人工恢复；自动暂停在条件消失后自行恢复；两者在 `dump` 与看板里可分辨。
- [x] 畸形或越权的 pending 文件被拒绝且不改变状态（fail-closed），错误信息指出问题所在。
- [x] 所有交互式介入路径都有一条超时用例——不存在「必须有人点一下才继续」的分支。

## 结论

意图即文件：`pending/<id>.json` 是请求，`intents/applied|refused/<id>.json` 是回执。`placeIntent` 是唯一写入口（CLI 今天用、UI 以后用），独占创建，谁也覆盖不了谁的事实。21 条测试，含一条 21 行的畸形/越权意图表（逐条断言回执原因 + 事实指纹未变）。

**「不会永久等人」是构造出来的，不是检查出来的：** 一个 hold 没有 `deadline_ms` 会被直接拒绝——「停在没人来的人类身上」这个状态不可表达。超时后事件里写 `fallback:true, decision_source:'timeout'`，而不是「已批准」。
