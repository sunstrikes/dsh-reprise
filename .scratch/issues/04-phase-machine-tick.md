# 04: 相位机 —— 一个候选从 LAND 走到 DONE，崩溃能接上

**What to build:** 确定性的相位机。一个候选从 LAND 走完九个候选相位到达 DONE 全靠代码推进；外部平台、候选实现者、模型判断、时钟全部是注入的端口；进程在任意点被杀掉之后，重启能接上而不是从头开始。这一票之后「无人值守」在代码层成立，只是各端口还是玩具。

**Blocked by:** 03（事实面：事件、状态、绑定、台账）

**Status:** resolved

- [x] 假端口下，一个候选走完 LAND → BUILD → VERIFY → SUBMIT_QUEUED → SUBMIT → MONITOR_POLL → CAND_ANALYZE → DONE；`dump` 能逐步看到每一步。
- [x] 一个 tick 对每个候选最多推进一步；反复 tick 同一状态不产生重复推进。
- [x] gate 给出 `missing` / `conflict` / `invalid` 时候选进 REJECTED，事件里留下四态结论与原文。
- [x] 「提交后、作业行写入前」硬杀进程：重开同一工作区，**先问平台**再推进，adopt 已有作业，平台侧始终只有一个作业（不重投）。
- [x] 宽限期：刚提交的作业在平台上暂时查不到时判 `unknown`，不判 `lost`。
- [x] 崩溃注入至少覆盖三个窗口：事件已落但状态未推进、预算已预扣但作业行未写、gate 已冻结但相位未推进。
- [x] 内核不读系统时钟，时间只从端口进入——每个用例因此可复现，不需要真的等。

## 结论

`packages/core/lib/loop.js`。全套 56/56，其中相位机 15 条。整条生命周期在假端口下跑通：`candidate_created` 到 `cand_analyze` 八个事件、零次模型调用、零次真实等待。

### 这一票把 02 的一个 bug 照出来了

`requirementsAt('LAND')` 要求 `parent_binding`，而 `parent_binding` 正是 **LAND 要产出的**。同一个 off-by-one，只是往左挪了一个边界——02 写完时我专门写了「phase 不得索要自己即将产出的东西」的回归测试，但那条只覆盖了 `VERIFY` 与 `SUBMIT`，漏了链头。

修法只有一处（`requirementsAt`），因为 02 把它定成了唯一入口。**这就是收口子的实际回报**：否则同样的判断会散落在 tick 的每个 case 里，改完一处还漏三处。

### 票面没定、我定了的三件事

1. **`applied_seq` 表示「没有事件在等着被折叠」，不是「最后一次改了状态」。** `reconcile` 写出的 `job_grace_period` / `job_state_corrected` 不改相位，但也要把 `applied_seq` 推过去——否则它们会在下次重启时被当成待折叠积压，让「落后」这个指标说谎。测试抓到的正是这个：第三次 `reconcile` 仍在「重放」，因为它自己上一次的输出没被算作已折叠。
2. **gate 判否 ≠ 产物不合法。** 第一版把「候选没通过验证」也标成 `status: 'invalid'`，那正好把四态要区分的东西又混起来：`invalid` 是「产物不合契约」，而「验证没通过」是一个**合法**产物所表达的结论。现在后者不带 `status`，只有契约拒绝时才带。
3. **BUILD 在模型模式下发一条 `build_skipped` 事件，而不是静默跳过。** 静默跳过会让时间线上出现相位跳跃，而「这个候选为什么没构建」是三个月后还会被问的问题。

### 崩溃窗口覆盖到四个

| 注入点 | 结果 |
|---|---|
| `after_submit`（平台知道、我们不知道） | 重启后 adopt，平台侧仍然只有一个作业 |
| `after_event`（事件已落、状态未推进） | 重启后折叠补上，`applied_seq` 追平 |
| `after_binding`（绑定已冻结、事件未落） | 绑定在、相位没动；重走该相位时 `freezeBinding` 返回 duplicate 而不是冲突 |
| 预算已预扣、作业行未写 | 被 `after_submit` 那格覆盖（预扣发生在更早的 SUBMIT_QUEUED） |
